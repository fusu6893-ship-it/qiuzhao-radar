# 秋招雷达 · AI 求职工作台

面向应届毕业生的 AI 求职产品：把「发现机会 → 判断匹配 → 定制简历 → 准备面试 → 跟踪结果」
串成一条连续的工作流，用同一个岗位档案承载全部求职资料。

这个仓库同时是两样东西：

1. **一个真正能操作的 Web 产品**（`index.html`）——五个模块都可以真实点击、生成、保存。
2. **一份产品经理作品集**（`portfolio.html`）——讲清楚用户痛点、产品架构、关键页面交互、
   AI 能力实现与 AI Coding 实践过程。

---

## 快速开始

不需要安装任何依赖，也不需要构建步骤。

### 方式一：直接打开（最简单）

双击 `index.html` 即可。所有「AI 能力」都在浏览器本地运行，可以完全离线使用。

> 注意：部分浏览器会限制 `file://` 协议下的本地存储，导致刷新后数据不保留。
> 如果需要完整的持久化体验，用下面两种方式之一。

### 方式二：本地起一个静态服务器（推荐）

```bash
cd 秋招助手
python3 -m http.server 8765
# 然后访问 http://127.0.0.1:8765/index.html
```

### 方式三：部署到静态托管

仓库是纯静态站点，可直接部署到 GitHub Pages / Vercel / Netlify / 对象存储，
把目录原样上传即可，无需构建命令。

## 核心设计

**以岗位为中心串联所有任务。** 每个岗位都是一个独立的求职项目：来源、JD、匹配分析、
简历版本、面试资料、进度记录都挂在同一个档案下。修改通用简历不会影响已投递岗位的历史版本。

**三条产品原则（直接影响功能设计）：**

- 信息可追溯：每条招聘信息与面经保留来源渠道、原始链接、最近核验时间，区分官方信息与社区线索。
- 内容可核验：AI 不编造经历。改写后缺少可验证数据的条目会标注「⚠️ 需补充事实」；
  AI 预测题与真实面经题使用不同标签。
- 用户可控：每条简历修改需用户逐条接受 / 修改 / 撤销；投递需用户手动确认，产品不自动投递。

## AI 能力是怎么实现的

原型内置一套**可解释的规则引擎**（`assets/js/ai.js`），包含五个能力：

| 能力 | 输入 → 输出 |
|---|---|
| JD 解析 | 粘贴的招聘文本 → 结构化的公司 / 岗位 / 城市 / 学历 / 截止时间 / 职责 / 要求 / 关键词 |
| 岗位匹配 | 个人画像 + 简历 + 岗位 → 匹配分 + 匹配优势（附简历原句证据）+ 能力差距 + 下一步建议 |
| 简历定制 | 简历 + JD → 逐条改写建议，含修改前 / 修改后 / 修改依据 / 是否需补充事实 |
| 面试题生成 | 岗位 + 面经库 + 简历 → 分类问题清单（真实面经题 / 预测题 / 简历追问）+ STAR 回答骨架 |
| 回答评估 | 用户回答 → 逻辑结构 / 岗位相关性 / 证据充分性 / 表达清晰度四维度评分 + 改进建议 + 追问 |

选择规则引擎而不是直接调用大模型，是为了让演示结果**稳定、可复现、可离线运行**。
生产环境中这套引擎会被替换为大模型调用，但产品层的关键词抽取、证据绑定、事实校验与
用户确认流程会保留——它们才是决定输出质量的部分。

设置页保留了 OpenAI 兼容接口的配置项，可切换到远程模型；请求失败会自动回退本地引擎。
浏览器直连第三方接口存在跨域与密钥暴露风险，正式部署建议通过自己的后端代理转发。

## 测试

AI 引擎的逻辑与产品化约束有 49 条自动化断言，可在任意 Node.js 环境运行（无需安装依赖）：

```bash
node tests/engine-test.js
```

断言覆盖的几类关键约束：

- AI 改写后不得出现原始简历中不存在的数字（防止编造数据）
- 面试预测题不得带来源，真实面经题必须保留来源链接与时间
- 匹配优势必须能追溯到简历中的具体句子
- 每条招聘信息必须带来源渠道与核验时间
- 新岗位的状态变更必须写入进度时间线

界面部分在真实浏览器中按用户路径逐项点检（首次引导、筛选、生成简历、模拟面试、
看板状态变更、窄屏布局等）。

## 数据说明（重要）

内置的岗位、公司、面经、简历**全部为虚构示例数据**，用于演示产品交互链路，
**不代表任何真实企业的招聘信息**，不可用于真实投递决策。

真实部署时应接入企业官方招聘页、官方接口或经授权的数据源；对于不支持自动采集的
公众号或小红书内容，应支持用户手动粘贴导入，避免把产品设计建立在不稳定的抓取能力上。
